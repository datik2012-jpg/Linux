When we done with configuration run:
>sudo netplan try
>ip route - check the routes

	
Those two lines define the DNS servers your system will use for name resolution. They tell Netplan to configure the interface to use 8.8.8.8 and 8.8.4.4 as DNS servers.	
Netplan writes these DNS servers into the backend resolver. You can verify with:
>resolvectl status
or check /etc/resolv.conf depending on your system. 


This means:

The destination network is 192.168.0.0/24  
(all IPs from 192.168.0.1 to 192.168.0.254)

To reach that network, your machine should send packets to the gateway 10.0.0.100.

In other words:

“If you want to reach any device in 192.168.0.x, forward the traffic to 10.0.0.100.”

This is a static route—useful when that network is behind another router.

- to: default
  via: 10.0.0.1
  
  is defines the default gateway.

to: default means “all traffic that doesn’t match any other route.”

via: 10.0.0.1 means “send it to 10.0.0.1.”

This is your internet gateway.

So:

“For everything else (web browsing, external networks), send traffic to 10.0.0.1.”


Destination	How traffic is routed
192.168.0.0/24	Forward to 10.0.0.100
Anything else	Forward to 10.0.0.1 (default route)

/////////////////Bridge and Bonding /////////


Bonding - when 2  enterfaces cards connected to the same network ( good for availability) if one of them fails second still working

Bonding mode 0 to 6
Mode 0 is default - Round Robin
     1 is active-backup   - uses only one interface and second keeps inactive only use the second in case of issue
	 2 is XOR - every transfer when start to use interface will use all packets to send with the same interface depends on the target mentioned jnt he packets
	 3 is broadcast - all data to all interfaces 
     4 is IEEE 802.3ad - can help increase network transfer rates 
	 5 is adaptive transmit load balancing  - will send the data to the interface which less busy 
	 6 is adaptive load balancing - trying to load balance both INCOMING and OUTCOMING trafics between both interfaces
	 
	 
	 
Bridge - connect two ore more networks together and act like one network
Bond - two or more connection to the network

///////////////////////////BOND ///////////////////////


If your goal is reliability or speed, choose bonding.
If your goal is connecting multiple interfaces or VMs into one LAN, choose bridging.

Bonding combines multiple network interfaces into one for redundancy or throughput, while bridging connects interfaces so devices on different segments behave as if they’re on the same Layer‑2 network.

What each one does
Bond (Link Aggregation / NIC Bonding) — Multiple physical NICs are merged into one logical interface. The goals are redundancy, failover, and sometimes higher throughput, depending on the bonding mode. 

Bridge (Layer‑2 Switch) — A virtual switch that connects two or more interfaces so all devices appear to be on the same LAN segment. No routing; it’s pure Layer‑2 forwarding.

Pros: Best for redundancy; no switch config needed

Netfilter Framework - is a subsystem

The Linux Netfilter Framework is the packet‑filtering and network‑manipulation subsystem built into the Linux kernel, providing hooks for firewalling, NAT, packet mangling, and connection tracking. 

Netfilter is a kernel‑level framework that lets modules inspect and manipulate packets as they traverse the Linux networking stack. It provides the foundation for tools like iptables and its modern successor nftables

Tools Built on Netfilter
Netfilter itself is the framework; the user interacts with it through higher‑level tools:

iptables
The traditional firewall interface for defining rulesets. Each rule contains matches (classifiers) and a target action. 

nftables
The modern replacement for iptables, offering:

More flexible and scalable rule sets

Better performance

A unified interface for IPv4, IPv6, ARP, and bridge filtering


What You Can Do With Netfilter
According to the official project documentation, Netfilter enables you to:

Build internet firewalls (stateless or stateful)

Deploy high‑availability filtering setups

Implement NAT gateways

Create custom packet‑processing modules 

Moder command to interact with Netfilter framework is NFT or iptables:


nftables vs iptables — What actually matters
🧠 1. Purpose and Architecture
Both are frontends to the Linux Netfilter framework, but they use different kernel modules:

iptables → ip_tables (legacy, multiple modules)

nftables → nf_tables (modern, unified)

nftables was created to fix iptables’ technical debt: fragmented tools, slow rule processing, and poor scalability.

Example: Block SSH from 10.0.0.5

iptables:
iptables -A INPUT -s 10.0.0.5 -p tcp --dport 22 -j DROP

nftables:
nft add rule inet filter input ip saddr 10.0.0.5 tcp dport 22 drop  

Performance & Scalability
iptables scans rules linearly, which becomes slow with large rule sets.

nftables supports sets and maps, enabling O(1) lookups for thousands of IPs or ports.

nftables updates rules atomically, avoiding race conditions and full ruleset reloads.

You’re showing an iptables DNAT port‑forwarding rule, and you want it written out cleanly as plain text for Notepad. Here it is exactly as it appears, formatted neatly:

sudo iptables -t nat -A PREROUTING \
    -i enp1s0 \
    -s 10.0.0.0/24 \
    -p tcp --dport 8080 \
    -j DNAT --to-destination 192.168.0.5:80



sudo iptables -t nat -A POSTROUTING -s 10.0.0.0/24 -o enp6s0 -j MASQUERADE


Dani, that command you showed is a MASQUERADE rule — the second half of a typical port‑forwarding/NAT setup on Linux.

This rule tells Linux:

Any traffic coming from the 10.0.0.0/24 network

And going out through interface enp6s0

Should have its source IP rewritten (SNAT) to the IP of enp6s0

Using MASQUERADE, which automatically adapts to dynamic IPs

In short:

✔ It allows devices on 10.0.0.0/24 to access the outside world
✔ It ensures return packets know how to get back
✔ It is required for DNAT/port‑forwarding to work correctly

Why you need this rule:

When you forward a port (DNAT), example:

PREROUTING → DNAT → 192.168.0.5:80


The server at 192.168.0.5 must reply back through your router.
Without MASQUERADE, the reply would go directly to the client and break the connection.

So this rule ensures:

Outgoing packets get rewritten

Replies return through the router

Port forwarding works end‑to‑end

NFT example:

now is the nftables version of the same port‑forwarding setup you previously built with iptables. This is the modern Netfilter ruleset, and it’s doing exactly the same job — just cleaner and more efficient.

>sudo ntf list ruleset

table ip nat {
    chain PREROUTING {
        type nat hook prerouting priority dstnat; policy accept;
        iifname "enp1s0" meta l4proto tcp ip saddr 10.0.0.0/24 tcp dport 8080 counter packets 0 bytes 0 dnat to 192.168.0.5:80
    }

    chain POSTROUTING {
        type nat hook postrouting priority srcnat; policy accept;
        oifname "enp6s0" ip saddr 10.0.0.0/24 counter packets 0 bytes 0 masquerade
    }
}

Cause:
10.0.0.x  →  enp1s0  →  ROUTER  →  enp6s0  →  192.168.0.5


Why MASQUERADE is needed (the real reason)

10.0.0.x → enp1s0 → DNAT → 192.168.0.5:80

Now the server replies:

192.168.0.5 → 10.0.0.x

NOte: Without MASQUERADE, the server tries to send the reply directly to 10.0.0.x
It bypasses the router → the client drops the packet → connection breaks.

With MASQUERADE:

192.168.0.5 → enp6s0 → Router rewrites source → 192.168.0.1 → enp1s0 → 10.0.0.x
Now the reply goes back through the router, and the router knows how to deliver it.

///////////////////Implement Reverse Proxies and Load Balancers ///////

What a reverse proxy is

A reverse proxy is a server that sits in front of your backend servers and handles requests on their behalf.

Think of it as:

A smart middleman that clients never see.

Clients think they’re talking to one server, but behind it you can have:

multiple web servers

multiple apps

containers

internal services

different ports

different machines

The reverse proxy hides all of that.

Why reverse proxies are needed (the real reasons)

1. One public IP → many internal services
You can run:

example.com → backend 1

api.example.com → backend 2

example.com/app → backend 3

All behind one IP and one port (80/443).

NAT cannot do this.
Port forwarding cannot do this cleanly.
Reverse proxies excel at this.


2. SSL termination
The reverse proxy handles HTTPS:

It receives encrypted traffic

Decrypts it

Sends plain HTTP to your internal servers

Your backend servers don’t need certificates at all.

3. Load balancing
A reverse proxy can distribute traffic across multiple servers:


Client → Reverse Proxy → Server A
Client → Reverse Proxy → Server B
Client → Reverse Proxy → Server C


4. Security
Reverse proxies can:

hide your internal network

block bad requests

rate‑limit

filter bots

add WAF (Web Application Firewall)

protect backend servers from direct exposure

Your backend servers never face the internet directly.

5. Caching
Reverse proxies can store static content:

images

CSS

JS

API responses

This makes your site faster and reduces backend load.


Load Balancers - balance trafic between multiple servers

NGINX  uses a two‑folder system to separate:

/etc/nginx/sites-available and /etc/nginx/sites-enabled


This folder is like a library.
You can keep:

test configs

disabled sites

staging configs

old versions

multiple domain configs

They exist, but they’re not active.

Only the active site configs: /etc/nginx/sites-enabled

Why this system is needed

Easy enable/disable of sites - "SOFT LINK"

sudo ln -s /etc/nginx/sites-available/mysite.conf /etc/nginx/sites-enabled/

Disable a site:

sudo rm /etc/nginx/sites-enabled/mysite.conf

2. Clean organization
You can keep dozens of configs in sites-available without cluttering the active list.

3. Safe testing
You can prepare a config in sites-available, test it, and only enable it when ready.

4. Standard across Linux distros
This structure comes from Debian/Ubuntu and is now widely used.
It keeps things predictable for admins and automation tools.


hen you use these folders
You use them when:
hosting multiple websites

hosting multiple apps

using reverse proxies

using SSL certificates

running staging + production on the same server

managing complex routing setups

You don’t need them when:
running a single simple site

using only the default config

using NGINX inside a Docker container (usually one config file)

But even then, the structure is still helpful.

Quick mental model
Think of it like this:

sites-available = storage room

sites-enabled = what’s actually plugged in and running

NGINX only looks at what’s plugged in.

PermitRootLogin forced-commands-only → Only allowed for automated restricted commands.

This means:

No one can SSH directly as root@server.

You must log in as a normal user and then use sudo for admin tasks.

This is considered a best‑practice security setting because it reduces brute‑force attack risk.



PasswordAuthentication no

means your SSH server will not allow password logins at all.

Only SSH keys can be used to log in.

So:

You cannot SSH using a username + password.

You must use an SSH keypair (id_rsa, id_ed25519, etc.).

Brute‑force password attacks become useless.

It’s a common hardening step on production servers.


KbdInteractiveAuthentication no

means SSH will not allow keyboard‑interactive authentication.

Here’s what that actually means in practice.

It’s an SSH authentication method where the server can ask the client any kind of prompt, such as:

“Password:”

“Enter OTP code:”

“Security question:”

“Enter verification token:”

It’s more flexible than simple password auth, and it’s often used for:

Two‑factor authentication

One‑time passwords (OTP)

Duo / Google Authenticator

PAM‑based challenges

When you connect to an SSH server for the first time, your SSH client receives the server’s public host key.
From that key, SSH generates a fingerprint — a short, unique identifier.

Example:ECDSA key fingerprint is SHA256:abc123...
This fingerprint is stored in: ~/.ssh/known_hosts
This file is your SSH client’s memory of which server is which.

Why fingerprints are needed
They protect you from man‑in‑the‑middle attacks.

When you connect again later, SSH checks:

“Does the server’s fingerprint match what I saw last time?”

If it matches, SSH connects normally.
If it does NOT match, SSH warns you:

WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!

This could mean:

The server was rebuilt

The SSH keys were regenerated

You connected to the wrong IP

Someone is trying to intercept your connection (MITM attack)

So fingerprints are a security check.

We can remove fingerprint stored for the server with IP address:

>ssh-keygen -R 10.0.0.251 

You use it when:

The server was reinstalled

The SSH host keys changed

You moved the IP to a different machine

You want SSH to “forget” the old identity

After removing it, the next SSH connection will ask:

Are you sure you want to continue connecting?

And then it stores the new fingerprint.

To remove all fingerprints we can remove entire the file:

>rm ~/.ssh/known_hosts 

This deletes all saved fingerprints.

SSH will treat every server as “new” again.

This is useful when:

You’re in a lab environment

You rebuilt many VMs

You don’t care about old fingerprints

You want a clean slate

But it’s less safe, because you lose all protection against MITM attacks until fingerprints are re-learned.

Only the client machine that stored the old fingerprint will get the warning.  
Nobody else sees it.
